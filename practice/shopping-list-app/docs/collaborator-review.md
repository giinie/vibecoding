# 협업자 리뷰: 개선 권장사항

> **작성일**: 2026-02-16
> **대상**: 프로젝트 기여자 (Gi-in Jeong)
> **목적**: 보안 감사 과정에서 관찰된 개발 프로세스 개선점 정리

---

## 전체 평가

보안 강화 Phase 1-4 → 후속 조치까지의 흐름이 체계적이었다. JWT 인증, helmet, rate limiting, input validation 등 주요 보안 레이어가 빠짐없이 도입되었고, 테스트 인프라(in-memory DB, module cache 관리)도 잘 구성되어 있다.

아래는 앞으로의 개발에서 **더 좋아질 수 있는 부분**이다.

---

## 1. 초기 설계 시 보안 체크리스트 활용

### 관찰

JWT 도입 시 `algorithm` 옵션이 빠졌고, 이메일 정규화가 누락되었다. 두 가지 모두 JWT/이메일 처리의 **잘 알려진 필수 항목**이다.

### 권장

새로운 인증/인가 기능을 구현할 때, 아래와 같은 체크리스트를 사용한다:

```
[ ] JWT: 알고리즘 명시 (sign + verify 모두)
[ ] JWT: 토큰 만료 시간 설정
[ ] 비밀번호: 해시 + 솔트 (bcrypt/argon2)
[ ] 이메일: 대소문자 정규화 + trim
[ ] 입력값: typeof 검증 + 길이 제한
[ ] ID: UUID 형식 검증 (URL param + body 모두)
[ ] 에러 메시지: 내부 정보 노출 여부 확인
```

**핵심**: 기능 구현이 끝난 뒤가 아니라 **설계 단계에서** 이 항목들을 확인하면 후속 감사에서 발견되는 이슈가 크게 줄어든다.

---

## 2. 검증 레이어 일관성

### 관찰

- URL param의 UUID는 `validateUuid` 미들웨어로 검증하지만, POST body의 `user_id`는 검증이 없었다.
- `title`/`message` 길이는 검증하지만 타입(typeof)은 검증하지 않았다.

### 권장

입력 검증은 "전부 하거나 안 하거나"가 아니라 **경로별로 빠지기 쉽다**. 검증을 추가할 때 아래 질문을 던진다:

> "이 데이터가 들어올 수 있는 **모든 경로**에서 동일한 검증을 거치는가?"

실용적인 방법:
- **미들웨어 레벨**: URL param → `validateUuid` (이미 잘 되어 있음)
- **컨트롤러 진입부**: body 필드 → 타입 + 형식 + 길이를 한 곳에서 일괄 검증
- 향후 규모가 커지면 `joi`나 `zod` 같은 스키마 검증 라이브러리 도입도 고려할 만하다

## 3. 에러 처리의 "정보 유출" 관점

### 관찰

- `bcrypt.compare()` 에러가 500으로 전파되어, 401(사용자 없음)과의 응답 차이로 계정 존재 여부를 추론할 수 있었다.
- NODE_ENV 미설정 시 에러 메시지가 클라이언트에 노출되었다.

### 권장

에러 핸들러를 작성할 때 항상 자문한다:

> "이 에러 응답이 공격자에게 **어떤 정보를 주는가?**"

구체적으로:
- **인증 관련 에러**: 성공/실패 경로의 응답 형태와 타이밍을 가능한 한 동일하게 유지
- **글로벌 에러 핸들러**: `development` opt-in 방식 (기본은 숨김)
- **DB 에러**: 제약 위반 메시지를 그대로 전달하지 말고, 사용자 친화적 메시지로 변환

## 4. 테스트에서 "실패 케이스" 비중 높이기

### 관찰

기존 51개 테스트 중 실패/에지 케이스 테스트 비율이 상대적으로 낮았다. 오늘 추가한 18개 테스트는 대부분 "잘못된 입력 → 400" 유형이다.

### 권장

새 기능을 추가할 때 테스트 비율 가이드라인:

```
성공 케이스 (happy path)     : 30-40%
실패 케이스 (validation)     : 30-40%
에지 케이스 (boundary, null) : 20-30%
```

특히 보안 관련 엔드포인트는 **실패 케이스가 더 중요하다**. "이 엔드포인트가 거부해야 하는 입력"을 먼저 나열하고 테스트를 작성하면 검증 누락을 사전에 방지할 수 있다.

## 5. 환경별 설정 관리

### 관찰

- `TRUST_PROXY`, `NODE_ENV`, `CORS_ORIGIN` 등 환경변수가 코드 여러 곳에 분산되어 있다.
- `.env.example` 파일이 없어 새 팀원이 필요한 환경변수를 파악하기 어렵다.

### 권장

프로젝트 루트에 `.env.example` 파일을 유지한다:

```env
# Required
JWT_SECRET=your-secret-here

# Optional (defaults shown)
PORT=3001
NODE_ENV=development
CORS_ORIGIN=http://localhost:3000
JWT_EXPIRES_IN=7d
TRUST_PROXY=          # Set to 1 behind reverse proxy
```

이 파일은 Git에 커밋하고, 실제 `.env`는 `.gitignore`에 포함한다. 환경변수를 추가할 때마다 `.env.example`도 함께 업데이트하는 습관을 들인다.

## 6. 범위 외 항목에 대한 후속 계획

### 관찰

보안 감사에서 "범위 외"로 분류된 항목들(토큰 폐기, httpOnly 쿠키, WebSocket rate limiting, 계정 열거 방지, HTTPS)은 프로덕션 배포 전에 반드시 해결해야 한다.

### 권장 우선순위

| 순위 | 항목 | 이유 |
|------|------|------|
| 1 | localStorage → httpOnly 쿠키 | XSS로 토큰 탈취 가능, 가장 높은 리스크 |
| 2 | JWT 토큰 폐기 (블랙리스트) | 토큰 유출 시 무효화 수단이 없음 |
| 3 | 계정 열거 방지 | 409 응답이 이메일 존재 여부를 노출 |
| 4 | WebSocket Rate Limiting | DoS 공격 벡터 |
| 5 | HTTPS 강제 | 배포 환경에서 설정 (Nginx/CDN 레벨) |

각 항목에 대한 상세 설계를 **별도 계획 문서**로 작성한 뒤 구현하는 것을 권장한다.

## 요약

| 영역 | 현재 수준 | 권장 행동 |
|------|-----------|-----------|
| 보안 체크리스트 | 사후 감사로 발견 | 설계 시 체크리스트 선행 적용 |
| 입력 검증 | 부분적 커버 | 모든 입력 경로에서 일관된 검증 |
| 에러 처리 | 정보 유출 가능성 존재 | "공격자 관점" 자문 습관화 |
| 테스트 전략 | 성공 케이스 중심 | 실패/에지 케이스 비중 확대 |
| 환경 설정 | 코드에 분산 | `.env.example` 중앙 관리 |
| 보안 로드맵 | 범위 외 항목 잔존 | 우선순위별 별도 계획 수립 |

전체적으로 보안 의식과 구조적 접근이 양호하다. 위 항목들은 "못하는 것"이 아니라 "더 빨리 잡을 수 있었던 것"에 해당한다. 체크리스트와 습관의 문제이며, 이미 올바른 방향으로 가고 있다.
